# Handover: building Villacana like the real place

This is the working spec for any agent (Claude, Codex or a person) continuing the
game build. It assumes the rules in `AGENTS.md`. The goal is a walkable Villacana
that someone who knows it recognises: structure first (lanes, walls, openings,
levels), then materials, then planting and small details.

## What is already in place

- **A reference graph.** Every photo, map screenshot and web photo is catalogued by
  area in `refs/` (generated by `scripts/build_references.py`):
  - `refs/README.md`: the index. `refs/areas/<area>.md`: one brief per area with
    its photos (best first), known facts, open questions, docs, data and code.
    `refs/topics/<topic>.md`: the same by topic (levels, materials...).
  - `refs/graph.json`: nodes for areas, topics, references, model features and
    build tasks, placement packets, registration landmarks and discrepancies.
    `cites` only means an author used a photo. `checked-against` retains render/photo
    diagnostics as `photoVerification`. `verification` is now strict placement
    status; only `placement-verified-by` grants approval within its metre tolerance.
    Open discrepancies override positive checks. Read `docs/PLACEMENT_VERIFICATION.md`.
    `refs/QUEUE.md` lists gaps in newer photo-check records; earlier manual reviews
    may exist and are not erased by this backlog.
  - Contact sheets of numbered thumbnails per area are in the private
    `villacana-reference` repo (`contact-sheets/<area>.jpg`).
- **Photo metadata you can trust to a stated degree.** `public/photos-ref/manifest.json`
  has each camera pin with GPS accuracy and altitude. Ground shots read 9 m altitude
  or less, roof and upper-floor shots more. Pins worse than about ±8 m are corrected
  from photo content where possible (`data/photo_positions.json`, original GPS kept).
  `data/reference_tags.json` says what each picture shows, from where, and, for key
  photos, what it is pointed at (`looksAt`, `subject`).
- **Worked examples of photo-backed building.** Copy their pattern:
  - `docs/ELENA_NORTH.md`: gateway, patio wall, raised beds, planters; and the
    steps beside the Cervantes ramp with a local terrain change.
  - `docs/MIDDLE_POOL.md`: east gateway and the raised west planter.
  - `docs/FRONTAGE_DIVISIONS.md`, `docs/DALI_CERVANTES.md`, `docs/LAYOUT_ACCURACY.md`.
  Each feature is a data file with `evidence` and `trust`, a `src/` module that
  builds meshes, collision rings and Details-only sprites, a drawing block in
  `src/blueprint.ts`, a `scripts/check_*.py`, and checks in the browser test.
- **The build queue.** `data/build_queue.json` lists the tasks; `refs/QUEUE.md`
  shows them by priority; `refs/issues/<task>.md` is a ready-to-file issue body
  for each open task.

## Photo inventory before a geometry task

Use [REFERENCE_PACK_WORKFLOW.md](REFERENCE_PACK_WORKFLOW.md) to make numbered
source locators/traces, a feature checklist and schematic relationship/form
drawings before a new scene build. The entrance pilot exposes the difference
between a floor citation and a fully accounted-for covered passage. Keep source
groups separate until connections are established. This complements the existing
measured placement gate and never grants placement approval.

## Taking a task

1. Pick an `open` task from `refs/QUEUE.md` whose `dependsOn` tasks are `done`.
   Highest priority first (P1, then P2, P3).
2. Branch `task/<task-id>` from `main`. Set the task's `status` to `in-progress`
   and `owner` to yourself in `data/build_queue.json`, in your first commit.
3. Read the issue body (`refs/issues/<task-id>.md`), the area brief and its
   contact sheet, then every listed photo at full size.
4. Check each photo's camera first. If the pin or heading disagrees with what the
   photo shows (a pin inside a gateway, a compass pointing away from the subject),
   correct it from photo content in `data/photo_positions.json` and the manifest
   (`trust: "checked against photo content"`, a `locationBasis`, original `gps`
   kept), and give every photo you build from a `looksAt` and `subject` in
   `data/reference_tags.json`. Then render the current game from those cameras
   before you change anything:
   `node scripts/shoot_views.cjs IMG_xxxx --pool=<pool> --task=<task-id> --as=before`
   (also saved to `docs/reviews/<task-id>/`; `--high` looks down from above for
   roof shots). Note how it differs from the photo.
5. Measure the photo, not just the scene: with a known width (a gate opening,
   0.2 m tiles, a 1.2 m lane) and the horizon, read how far along the path each
   part sits and in what order (gate, planter, bench...). Write those distances into
   the data's `trust`. Trace positions against `public/map/ground.jpg` (bounds in
   `public/map/ground.json`), the registry footprints and the road lines in
   `public/map/skeleton.json`. Map metres: +x east, +z south. A camera pin
   locates the camera, not the subject; roof shots stand inside buildings. Save a
   reviewable alignment/discrepancy report before editing geometry: one global
   registration, distributed controls and separate held-out landmarks, metre
   errors including uncertainty, labelled ground/roof outlines and proposed
   bounded corrections. Record concealed boundaries as unresolved. Declare the
   task's affected raw feature IDs in `features`.
6. Build the feature in its own data file and module, following the examples.
   Record `evidence` (photo files) and an honest `trust` sentence saying what is
   photo-supported and what is estimated.
7. Render again from the same cameras (`--as=after`) and put each render beside its
   photo. Check order and spacing along the path, which side things are on, and that
   nothing moving (an open gate leaf) sits in front of something it should not.
   Record one entry per photo in `data/photo_checks.json`: `matches`, or `differs`
   with notes and a new open task as `followUp` for what is still wrong.
8. Set the task `done`, add any new fact or open question to the area's `notes`
   in `data/areas.json`, add newly discovered work as new tasks (with photos),
   and rebuild the references. New geometry tasks also require a fresh measured
   placement packet for every declared feature, independently reviewed against
   actual maps and full-size photos. Keep them in progress if this approval is
   unavailable. Follow `docs/PLACEMENT_VERIFICATION.md` for packets and discrepancy
   resolution; a later match or a closed task cannot erase an open discrepancy.

## Definition of done (every task)

Run from the repo root; all must pass:

```bash
python3 scripts/assign_photo_map.py && python3 scripts/test_photo_assignment.py
python3 scripts/build_references.py --check
python3 scripts/test_reference_index.py && python3 scripts/test_placement_verification.py
python3 scripts/check_placement_changes.py --base origin/main
cd scripts && for c in check_map check_street_layout check_boundary_reference check_terrain \
  check_dali_threshold check_cervantes_patio_walls check_elena_north check_middle_pool check_paseo_wall \
  check_seafront check_pool_levels check_levels check_lowered_lanes check_seafront_fence; do python3 $c.py | tail -1; done; cd ..
npx tsc --noEmit && npm run build
node scripts/test_layout_browser.cjs
node scripts/test_overview_browser.cjs
node scripts/test_photo_map_browser.cjs
```

Plus the task's own `Done when` items, a new or extended `scripts/check_*.py`
for what you built, and before/after renders from the photo cameras committed in
`docs/reviews/<task-id>/` and recorded in `data/photo_checks.json`.
For tooling/audit tasks without geometry changes, record applicable evidence and
software outcomes instead of inventing photo-camera pairs or placement approvals.
The Evidence graph PR check must pass before merge. It validates records, hashes
and arithmetic; independent source inspection still establishes what images show.
`build_references.py --check` fails for a done task with an unchecked photo, a
`differs` without an open follow-up, or a checked photo without a reviewed `looksAt`.
Passing source checks and walking tests does not show the build looks like the place.
Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` if Playwright cannot find a browser.

## Rules that matter most

- Build only what photos support. If a photo does not show where a wall ends,
  stop it where the photo stops and say so. Never fill gaps with repeated walls,
  gates or scenery.
- Keep every lane walkable: walls keep each route's half-width clear; openings
  stay open unless a photo shows them shut. The browser test walks all routes
  both ways.
- Map, 3D and collision use the same outlines.
- Registry house and pool footprints stay as they are unless a photo-backed
  correction is the point of the task.
- Level changes go through `data/terrain.json` (see `localRuns`) and need
  `check_terrain.py` updated; steps give the player stepped ground. Heights come
  from `data/levels_survey.json` (`docs/LEVELS.md`): houses stay at lane level,
  patios and terraces are what is raised.
- Layout view shows structure; plants, hedges and props are Details only and
  must pass the route-clearance guard.
- This repo is public: no API keys, signed URLs, photo metadata blobs or fetched
  Google imagery. Private reference images stay in `villacana-reference`.

## Working alongside other agents

- One task per branch and PR. Keep edits to shared files (`src/slice.ts`,
  `src/blueprint.ts`, `scripts/assign_photo_map.py`,
  `scripts/test_layout_browser.cjs`, `data/areas.json`) to small, separate lines.
- Generated files conflict often: `public/photos-ref/assignments.json`,
  `public/photos-ref/evidence-graph.json` and everything in `refs/`. Never
  hand-merge them; take either side and regenerate with `assign_photo_map.py`
  and `build_references.py`.
- Contact sheets live in the private repo; rebuild them with
  `build_references.py --sheets` only when you can commit to that repo too.

## New photos

Originals go in Google Drive (folder "Villacana") or in
`villacana-reference/uploads/`. Follow "Intake for a new Drive batch" in
`docs/PHOTO_MAP_WORKFLOW.md`: index, describe, tag (`shows`, `viewpoint`,
`useFor`, and `looksAt`/`subject` for roof shots and build sources), check
altitude against viewpoint, correct vague pins from photo content, rebuild.
Then add any build work the photos reveal to `data/build_queue.json`.

## Splitting the queue into issues

The open tasks are filed as GitHub issues (#31-#51, #54-#57) (each task's `issue` field
in `data/build_queue.json`); close the issue from the task's PR with
`Closes #<n>`. For new tasks: each open task has a body in `refs/issues/<task-id>.md` with the area, the
photos (with pin accuracy and subject), what to build, what not to do and a
checklist. File one issue per task with that body and the task title, label it
with its area and priority, and reference the task id in the PR that closes it.
