# One map and a complete photo index

The app root is the canonical entry. Map & photos uses `src/blueprint.ts`'s detailed
registry map; Overview and Walk embed the existing `src/slice.ts` renderer for
north, middle, south and main pools plus the seafront. The separate OSM default
and simplified photo-map browser modules have been retired. Old `blueprint.html`
and `photos.html` links preserve query parameters, selected-photo IDs and hashes
while redirecting to the root. Diagnostic `slice.html` links remain usable.

## Find and cite a photo

- Search a stable ID, visible subject, caption or area; choose an area filter if useful.
- Camera IDs are on by default in Map & photos and Overview. Labels declutter at
  crowded zoom levels; every source remains available in the list. Selecting an
  overview ID opens its photo card in Map & photos.
- The card opens the full public JPEG or links to the private repository. Private
  and unplaced sources are searchable; neither receives an invented camera pin.
- Copy photo link reopens the chosen ID. Copy agent reference includes the source
  path, published caption, local draft if any, camera uncertainty, separate subject
  point and its basis, notes, model citations and recorded checks.
- Source/citation counts are not accuracy scores. Missing recent check records do
  not erase earlier manual reviews. Reviewed look-at points are approximate subject
  landmarks, not surveyed boundaries.

`public/reference-index.json` is generated by `scripts/build_references.py` from
the same catalogue, tags and evidence records as `refs/`. It contains all 172
current references: 145 public photos (144 with cameras) and 27 private sources.
No private pixels are embedded. Builds regenerate associations and references
before producing the application; missing or untagged sources fail the reference
check instead of silently disappearing from the list.

Agents can use the same index without browser interpretation:

```bash
python3 scripts/find_reference.py boat
python3 scripts/find_reference.py --area north-pool --json
```

Camera coordinates in this index use the skeleton's original metre frame (+x
east, +z south). Display rotation is applied only by the view; pins are not snapped
to geometry. A selected camera shows reported uncertainty (or a clearly marked
10 m heuristic when unknown), heading and a separate reviewed subject cross.

## Barraka boat: source review

Inspected the private Barraka contact sheet and full public IMG_2223, IMG_2346 and
IMG_2347. IMG_2223 clearly shows a pale, sand-filled boat with logs and smoke;
IMG_2346/2347 establish the same boat beside the planted BARRAKA BEACH sign, on
the left of the timber boardwalk looking seaward. It is a barbecue/cooking boat,
not a planter. The old label is corrected and all three references now findable
by searching “boat”. Existing boardwalk/sign geometry and the independently
anchored aerial position are documented in [BARRAKA_BOARDWALK.md](BARRAKA_BOARDWALK.md).

The reviewed subject point [37,126] is a discovery landmark approximately 3 m in
precision. It is not a hull survey. Recorded camera positions [39.3,102],
[35.6,95.2] and [35.3,96.5] are about 24–31 m inland of that subject; the earlier
content confirmation on IMG_2346 does not validate these coordinates. Their
reported uncertainty is preserved and the contradictory evidence is visible in
the card and copied reference. No camera correction is invented.

The boat has no mesh/collision footprint in the current model. Existing citations
link these photos to boardwalk/sign/seating features, not to a boat. The new open
task `barraka-barbecue-boat` records that omission and the required placement,
measurement and shared geometry checks. This UI/source-discovery task changes no
buildings, pools, paths, terrain or collision; it does not claim a photographic
match or area-wide fidelity.

## Persistence and compatibility

Existing annotation (`villacana-reference-points-v1`), caption/object
(`villacana-map-edits`) and camera-review (`villacana-photo-checks-v1`) stores are
retained. New caption saves update the map's editing state so a later object save
does not overwrite them. Correct/unsure/moved camera proposals and notes retain
the original export format accepted by `apply_photo_reviews.py`. Saving locally
does not publish a correction. Clipboard failure exposes text for manual copying.
Public source links are stable by ID rather than array position. Private access
still requires membership in the private repository.
